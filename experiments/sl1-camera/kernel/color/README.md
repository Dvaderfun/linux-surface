# Surface Laptop 1: color-camera integration

The color driver already has an open [linux-surface/kernel PR, #186](https://github.com/linux-surface/kernel/pull/186). It was tested by its author on the **Laptop 2** and targets `v7.2-surface-devel`. The **Laptop 1** evidence here is for [Sam’s related three-patch series](https://github.com/linux-surface/linux-surface/issues/2401), not PR #186's unmodified head. The two solutions share the OVTI9734 bridge entry and clock/reset power sequencing. They are alternatives, not a six-patch series.

The [project's routing instructions](https://github.com/linux-surface/linux-surface/blob/a88004b01334adfd1d2957dc646a2a2664ddebb8/patches/README.md) say new kernel functionality goes to the latest `-surface-devel` branch. The newest live ref was `v7.3-surface-devel` at the time of review; the [generated 7.3 patch stack](https://github.com/linux-surface/linux-surface/commit/1e282dd7d1847eaff93f7deee589e1cbfe0698d4) has stable base v7.3.5, distinct from both the development tree (7.3.0) and the shipped Fedora 7.3.4-2 tested on the laptop. ## Validation

* **SL1 hardware, release build with Sam's three changes:** firmware 138.3732.768, DMI `Surface_Laptop`, single-lane OVTI9734 at I²C2 0x36 / CSI-2 port 1, MSHW0073, 19.2 MHz external clock. Real GNOME Camera preview and repeated 60-frame 1280×720 captures at 30.3–30.4 fps with patched libcamera/PipeWire. The kernel exposes 1296×734 raw Bayer; 1280×720 is the delivered *processed* resolution. The privacy indicator followed use and the sensor runtime-suspended after capture. These results do not establish Windows image-quality parity, system suspend on SL1, or desktop support with unmodified distribution libcamera.
* **Current development tree:** all three alternative patches apply without changing unrelated drivers. The final OV9734 C file is byte-identical to the implementation used for the hardware results. The bridge's only difference against the tested complete source is a pre-existing log/put ordering change in an IVSC error path, unrelated to the OVTI9734 table entry.
* **Native kernel build:** both `drivers/media/i2c/ov9734.o` and `drivers/media/pci/intel/ipu-bridge.o` built on the full pinned 7.3 development tree with `W=1` and no diagnostics. Used the tested Fedora config, `olddefconfig`, with BTF disabled and distribution signing-key paths cleared for this unsigned object build. This is not a full distro package build, reboot or target-kernel hardware test.
* **Compatibility:** also compiled and linked both proposed routes (including the two #186 follow-ups) with MODPOST against installed Fedora 7.3.4-2 surface headers. Kbuild noted a host `pahole` version mismatch; no compiler/ABI errors. With those headers, `.text` of the alternative's OV9734 module matched the installed signed OV9734 exactly (5,299 bytes, SHA-256 `0557a52ec1cd646a338ea374d6b82f00824493e6f5834212a848a8ce80128336`). The alternative and both #186 changes passed kernel `scripts/checkpatch.pl --no-tree` (`--no-signoff` for the deliberately unsigned review hunk).
* **Scope:** no live kernel, key, bootloader or camera setting was changed to prepare these patches. The PR #186 variant still adds regulator handling, uses different power-up delays and has its own cleanup paths; final hardware retesting by its author is needed before transferring a Tested-by to that exact implementation. Sam's original note explicitly says that the 1 ms clock-settle and 10 ms reset-release waits were empirically tested; they were not claimed to be datasheet limits. Testing of legacy ACPI-powered devices without these GPIOs is also distinct from the SL1 results.

For reproducible kernel builds, check out the pinned development commit, `git am /path/to/v7.3-alternative/*.patch`, configure a build directory with `CONFIG_VIDEO_OV9734=m`, `CONFIG_IPU_BRIDGE=m` and the normal Intel IPU3 prerequisites, then run `make O=/path/to/build W=1 drivers/media/i2c/ov9734.o drivers/media/pci/intel/ipu-bridge.o`. No signing key or running camera is needed.
